## 接下来先做什么

1. 将“原文与旁注”的记录流程迁入主应用，先完成存储兼容与恢复测试。
2. 定义 Findings 契约：实际记录 ID、精确原文引用、观察、假设与不确定性。
   当前主应用返回引用 ID，体验稿使用固定原文引用，两者尚未合并。
3. 接入真实 Copilot 流程：选择与确认发送范围、等待、取消、失败、重试。
   模型输出不可靠时不伪造发现、不修改原文，允许返回证据不足。
4. 将反馈、可选尝试、回访与日记关联持久化，验证完整闭环。
5. 单独验收提醒、导出、删除、备份与真实手机体验，再决定发布方案。

以上是待办，不表示已完成。通知、模型调用与跨设备能力不能由静态稿证明。

## Agent team 第一轮建议

团队启动时先确定一轮目标，建议是“新设计下的真实 Findings 闭环”。
先由主 Agent 明确数据契约和迁移策略，解决阻塞项，再开展并行任务。

| 角色 | 建议文件边界 | 验收重点 |
| --- | --- | --- |
| 主 Agent / 集成 | 数据契约、任务说明、合并和最终验收 | 隐私、兼容性、端到端流程 |
| 记录体验 Agent | 明确划定的界面与样式文件 | 原文保留、草稿恢复、手机排版 |
| Findings Agent | copilot-bridge.mjs 及明确划定的契约测试 | 精确引用、不确定性、取消与异常 |
| 验证 Agent | 独立验收文档和指定测试文件 | 无模型假象、无数据丢失、回访闭环 |

这只是建议角色，启动前必须明确每人的实际文件列表。
当前 `app.js` 集中处理多个流程，不适合让多个 Agent 同时修改；需要按轮次
安排唯一写入者，或先由主 Agent 做必要、有限的职责拆分。
不要为了“多 Agent”提前拆成大量模块，也不要让等待契约的任务空转。

## Git 工作方式

- 保留初始基线，按功能建立分支；提交描述说明变化与验证结果。
- 提交前检查变更文件、忽略规则、敏感信息和测试结果。
- 每轮先检查工作区，保留他人的未提交改动，不做破坏性清理。
- 新文件明确列入白名单；界面示例只能用标记清楚的虚构记录。
- 需要远程协作时，再由用户确认 GitHub 仓库、可见性和首次推送。
